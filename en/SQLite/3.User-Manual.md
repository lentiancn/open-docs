# SQLite User Manual

## 1. Summary

The following two objects and eight methods comprise the essential elements of the SQLite interface:

- **sqlite3** → The database connection object. Created by [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) and destroyed by [sqlite3_close()](https://www.sqlite.org/c3ref/close.html).
- **sqlite3_stmt** → The prepared statement object. Created by [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) and destroyed by [sqlite3_finalize()](https://www.sqlite.org/c3ref/finalize.html).
- **sqlite3_open()** → Open a connection to a new or existing SQLite database. The constructor for sqlite3.
- **sqlite3_prepare()** → Compile SQL text into byte-code that will do the work of querying or updating the database. The constructor for sqlite3_stmt.
- **sqlite3_bind()** → Store application data into parameters of the original SQL.
- **sqlite3_step()** → Advance an sqlite3_stmt to the next result row or to completion.
- **sqlite3_column()** → Column values in the current result row for an sqlite3_stmt.
- **sqlite3_finalize()** → Destructor for sqlite3_stmt.
- **sqlite3_close()** → Destructor for sqlite3.
- **sqlite3_exec()** → A wrapper function that does sqlite3_prepare(), sqlite3_step(), sqlite3_column(), and sqlite3_finalize() for a string of one or more SQL statements.

SQLite has more than 225 APIs. However, most of the APIs are optional and very specialized and can be ignored by beginners. The core API is small, simple, and easy to learn.

## 2. SQLite In 5 Minutes Or Less

Below is a simple C program that demonstrates how to use the C/C++ interface to SQLite. The name of a database is given by the first argument and the second argument is one or more SQL statements to execute against the database. The function calls to pay attention to here are the call to [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) on line 22 which opens the database, [sqlite3_exec()](https://www.sqlite.org/c3ref/exec.html) on line 28 that executes SQL commands against the database, and [sqlite3_close()](https://www.sqlite.org/c3ref/close.html) on line 33 that closes the database connection.

```c
#include <stdio.h>
#include <sqlite3.h>

static int callback(void *NotUsed, int argc, char **argv, char **azColName){
  int i;
  for(i=0; i<argc; i++){
    printf("%s = %s\n", azColName[i], argv[i] ? argv[i] : "NULL");
  }
  printf("\n");
  return 0;
}

int main(int argc, char **argv){
  sqlite3 *db;
  char *zErrMsg = 0;
  int rc;

  if( argc!=3 ){
    fprintf(stderr, "Usage: %s DATABASE SQL-STATEMENT\n", argv[0]);
    return(1);
  }
  rc = sqlite3_open(argv[1], &db);
  if( rc ){
    fprintf(stderr, "Can't open database: %s\n", sqlite3_errmsg(db));
    sqlite3_close(db);
    return(1);
  }
  rc = sqlite3_exec(db, argv[2], callback, 0, &zErrMsg);
  if( rc!=SQLITE_OK ){
    fprintf(stderr, "SQL error: %s\n", zErrMsg);
    sqlite3_free(zErrMsg);
  }
  sqlite3_close(db);
  return 0;
}
```

## 3. Core Objects And Interfaces

The principal task of an SQL database engine is to evaluate SQL statements of SQL. To accomplish this, the developer needs two objects:

- The [database connection](https://www.sqlite.org/c3ref/sqlite3.html) object: sqlite3
- The [prepared statement](https://www.sqlite.org/c3ref/stmt.html) object: sqlite3_stmt

Strictly speaking, the [prepared statement](https://www.sqlite.org/c3ref/stmt.html) object is not required since the convenience wrapper interfaces, [sqlite3_exec](https://www.sqlite.org/c3ref/exec.html) or [sqlite3_get_table](https://www.sqlite.org/c3ref/free_table.html), can be used and these convenience wrappers encapsulate and hide the [prepared statement](https://www.sqlite.org/c3ref/stmt.html) object. Nevertheless, an understanding of [prepared statements](https://www.sqlite.org/c3ref/stmt.html) is needed to make full use of SQLite.

The [database connection](https://www.sqlite.org/c3ref/sqlite3.html) and [prepared statement](https://www.sqlite.org/c3ref/stmt.html) objects are controlled by a small set of C/C++ interface routines listed below:

- [sqlite3_open()](https://www.sqlite.org/c3ref/open.html)
- [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html)
- [sqlite3_step()](https://www.sqlite.org/c3ref/step.html)
- [sqlite3_column()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_finalize()](https://www.sqlite.org/c3ref/finalize.html)
- [sqlite3_close()](https://www.sqlite.org/c3ref/close.html)

### Core Interface Functions

**sqlite3_open()**
This routine opens a connection to an SQLite database file and returns a [database connection](https://www.sqlite.org/c3ref/sqlite3.html) object. This is often the first SQLite API call that an application makes and is a prerequisite for most other SQLite APIs. Many SQLite interfaces require a pointer to the [database connection](https://www.sqlite.org/c3ref/sqlite3.html) object as their first parameter and can be thought of as methods on the [database connection](https://www.sqlite.org/c3ref/sqlite3.html) object. This routine is the constructor for the [database connection](https://www.sqlite.org/c3ref/sqlite3.html) object.

**sqlite3_prepare()**
This routine converts SQL text into a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) object and returns a pointer to that object. This interface requires a [database connection](https://www.sqlite.org/c3ref/sqlite3.html) pointer created by a prior call to [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) and a text string containing the SQL statement to be prepared. This API does not actually evaluate the SQL statement. It merely prepares the SQL statement for evaluation.

Think of each SQL statement as a small computer program. The purpose of [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) is to compile that program into object code. The [prepared statement](https://www.sqlite.org/c3ref/stmt.html) is the object code. The [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) interface then runs the object code to get a result.

New applications should always invoke [sqlite3_prepare_v2()](https://www.sqlite.org/c3ref/prepare.html) instead of [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html). The older [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) is retained for backwards compatibility. But [sqlite3_prepare_v2()](https://www.sqlite.org/c3ref/prepare.html) provides a much better interface.

**sqlite3_step()**
This routine is used to evaluate a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) that has been previously created by the [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) interface. The statement is evaluated up to the point where the first row of results are available. To advance to the second row of results, invoke [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) again. Continue invoking [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) until the statement is complete. Statements that do not return results (ex: INSERT, UPDATE, or DELETE statements) run to completion on a single call to [sqlite3_step()](https://www.sqlite.org/c3ref/step.html).

**sqlite3_column()**
This routine returns a single column from the current row of a result set for a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) that is being evaluated by [sqlite3_step()](https://www.sqlite.org/c3ref/step.html). Each time [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) stops with a new result set row, this routine can be called multiple times to find the values of all columns in that row.

There really is no such thing as a "sqlite3_column()" function in the SQLite API. Instead, what we here call "sqlite3_column()" is a place-holder for an entire family of functions that return a value from the result set in various data types. There are also routines in this family that return the size of the result (if it is a string or BLOB) and the number of columns in the result set.

- [sqlite3_column_blob()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_bytes()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_bytes16()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_count()](https://www.sqlite.org/c3ref/column_count.html)
- [sqlite3_column_double()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_int()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_int64()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_text()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_text16()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_type()](https://www.sqlite.org/c3ref/column_blob.html)
- [sqlite3_column_value()](https://www.sqlite.org/c3ref/column_blob.html)

**sqlite3_finalize()**
This routine destroys a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) created by a prior call to [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html). Every prepared statement must be destroyed using a call to this routine in order to avoid memory leaks.

**sqlite3_close()**
This routine closes a [database connection](https://www.sqlite.org/c3ref/sqlite3.html) previously opened by a call to [sqlite3_open()](https://www.sqlite.org/c3ref/open.html). All [prepared statements](https://www.sqlite.org/c3ref/stmt.html) associated with the connection should be [finalized](https://www.sqlite.org/c3ref/finalize.html) prior to closing the connection.

## 4. Typical Usage Of Core Routines And Objects

An application will typically use [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) to create a single [database connection](https://www.sqlite.org/c3ref/sqlite3.html) during initialization. Note that [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) can be used to either open existing database files or to create and open new database files. While many applications use only a single [database connection](https://www.sqlite.org/c3ref/sqlite3.html), there is no reason why an application cannot call [sqlite3_open()](https://www.sqlite.org/c3ref/open.html) multiple times in order to open multiple [database connections](https://www.sqlite.org/c3ref/sqlite3.html) - either to the same database or to different databases. Sometimes a multi-threaded application will create separate [database connections](https://www.sqlite.org/c3ref/sqlite3.html) for each thread. Note that a single [database connection](https://www.sqlite.org/c3ref/sqlite3.html) can access two or more databases using the [ATTACH](https://www.sqlite.org/lang_attach.html) SQL command, so it is not necessary to have a separate database connection for each database file.

Many applications destroy their [database connections](https://www.sqlite.org/c3ref/sqlite3.html) using calls to [sqlite3_close()](https://www.sqlite.org/c3ref/close.html) at shutdown. Or, for example, an application that uses SQLite as its [application file format](https://www.sqlite.org/appfileformat.html) might open [database connections](https://www.sqlite.org/c3ref/sqlite3.html) in response to a File/Open menu action and then destroy the corresponding [database connection](https://www.sqlite.org/c3ref/sqlite3.html) in response to the File/Close menu.

To run an SQL statement, the application follows these steps:
1. Create a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) using [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html).
2. Evaluate the [prepared statement](https://www.sqlite.org/c3ref/stmt.html) by calling [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) one or more times.
3. For queries, extract results by calling [sqlite3_column()](https://www.sqlite.org/c3ref/column_blob.html) in between two calls to [sqlite3_step()](https://www.sqlite.org/c3ref/step.html).
4. Destroy the [prepared statement](https://www.sqlite.org/c3ref/stmt.html) using [sqlite3_finalize()](https://www.sqlite.org/c3ref/finalize.html).

The foregoing is all one really needs to know in order to use SQLite effectively. All the rest is optimization and detail.

## 5. Convenience Wrappers Around Core Routines

The [sqlite3_exec()](https://www.sqlite.org/c3ref/exec.html) interface is a convenience wrapper that carries out all four of the above steps with a single function call. A callback function passed into [sqlite3_exec()](https://www.sqlite.org/c3ref/exec.html) is used to process each row of the result set. The [sqlite3_get_table()](https://www.sqlite.org/c3ref/free_table.html) is another convenience wrapper that does all four of the above steps. The [sqlite3_get_table()](https://www.sqlite.org/c3ref/free_table.html) interface differs from [sqlite3_exec()](https://www.sqlite.org/c3ref/exec.html) in that it stores the results of queries in heap memory rather than invoking a callback.

It is important to realize that neither [sqlite3_exec()](https://www.sqlite.org/c3ref/exec.html) nor [sqlite3_get_table()](https://www.sqlite.org/c3ref/free_table.html) do anything that cannot be accomplished using the core routines. In fact, these wrappers are implemented purely in terms of the core routines.

## 6. Binding Parameters and Reusing Prepared Statements

In prior discussion, it was assumed that each SQL statement is prepared once, evaluated, then destroyed. However, SQLite allows the same [prepared statement](https://www.sqlite.org/c3ref/stmt.html) to be evaluated multiple times. This is accomplished using the following routines:

- [sqlite3_reset()](https://www.sqlite.org/c3ref/reset.html)
- [sqlite3_bind()](https://www.sqlite.org/c3ref/bind_blob.html)

After a [prepared statement](https://www.sqlite.org/c3ref/stmt.html) has been evaluated by one or more calls to [sqlite3_step()](https://www.sqlite.org/c3ref/step.html), it can be reset in order to be evaluated again by a call to [sqlite3_reset()](https://www.sqlite.org/c3ref/reset.html). Think of [sqlite3_reset()](https://www.sqlite.org/c3ref/reset.html) as rewinding the [prepared statement](https://www.sqlite.org/c3ref/stmt.html) program back to the beginning. Using [sqlite3_reset()](https://www.sqlite.org/c3ref/reset.html) on an existing [prepared statement](https://www.sqlite.org/c3ref/stmt.html) rather than creating a new [prepared statement](https://www.sqlite.org/c3ref/stmt.html) avoids unnecessary calls to [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html). For many SQL statements, the time needed to run [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) equals or exceeds the time needed by [sqlite3_step()](https://www.sqlite.org/c3ref/step.html). So avoiding calls to [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) can give a significant performance improvement.

It is not commonly useful to evaluate the exact same SQL statement more than once. More often, one wants to evaluate similar statements. For example, you might want to evaluate an INSERT statement multiple times with different values. Or you might want to evaluate the same query multiple times using a different key in the WHERE clause. To accommodate this, SQLite allows SQL statements to contain [parameters](https://www.sqlite.org/lang_expr.html#varparam) which are "bound" to values prior to being evaluated. These values can later be changed and the same [prepared statement](https://www.sqlite.org/c3ref/stmt.html) can be evaluated a second time using the new values.

SQLite allows a [parameter](https://www.sqlite.org/lang_expr.html#varparam) wherever a string literal, blob literal, numeric constant, or NULL is allowed in queries or data modification statements. (DQL or DML) (Parameters may not be used for column or table names, or as values for constraints or default values. (DDL)) A [parameter](https://www.sqlite.org/lang_expr.html#varparam) takes one of the following forms:

- ?
- ?NNN
- :AAA
- $AAA
- @AAA

In the examples above, NNN is an integer value and AAA is an identifier. A parameter initially has a value of NULL. Prior to calling [sqlite3_step()](https://www.sqlite.org/c3ref/step.html) for the first time or immediately after [sqlite3_reset()](https://www.sqlite.org/c3ref/reset.html), the application can invoke the [sqlite3_bind()](https://www.sqlite.org/c3ref/bind_blob.html) interfaces to attach values to the parameters. Each call to [sqlite3_bind()](https://www.sqlite.org/c3ref/bind_blob.html) overrides prior bindings on the same parameter.

An application is allowed to prepare multiple SQL statements in advance and evaluate them as needed. There is no arbitrary limit to the number of outstanding [prepared statements](https://www.sqlite.org/c3ref/stmt.html). Some applications call [sqlite3_prepare()](https://www.sqlite.org/c3ref/prepare.html) multiple times at start-up to create all of the [prepared statements](https://www.sqlite.org/c3ref/stmt.html) they will ever need. Other applications keep a cache of the most recently used [prepared statements](https://www.sqlite.org/c3ref/stmt.html) and then reuse [prepared statements](https://www.sqlite.org/c3ref/stmt.html) out of the cache when available. Another approach is to only reuse [prepared statements](https://www.sqlite.org/c3ref/stmt.html) when they are inside of a loop.

## 7. Configuring SQLite

The default configuration for SQLite works great for most applications. But sometimes developers want to tweak the setup to try to squeeze out a little more performance, or take advantage of some obscure feature.

The [sqlite3_config()](https://www.sqlite.org/c3ref/config.html) interface is used to make global, process-wide configuration changes for SQLite. The [sqlite3_config()](https://www.sqlite.org/c3ref/config.html) interface must be called before any [database connections](https://www.sqlite.org/c3ref/sqlite3.html) are created. The [sqlite3_config()](https://www.sqlite.org/c3ref/config.html) interface allows the programmer to do things like:

- Adjust how SQLite does [memory allocation](https://www.sqlite.org/malloc.html), including setting up alternative memory allocators appropriate for safety-critical real-time embedded systems and application-defined memory allocators.
- Set up a process-wide [error log](https://www.sqlite.org/errlog.html).
- Specify an application-defined page cache.
- Adjust the use of mutexes so that they are appropriate for various [threading models](https://www.sqlite.org/threadsafe.html), or substitute an application-defined mutex system.

After process-wide configuration is complete and [database connections](https://www.sqlite.org/c3ref/sqlite3.html) have been created, individual database connections can be configured using calls to [sqlite3_limit()](https://www.sqlite.org/c3ref/limit.html) and [sqlite3_db_config()](https://www.sqlite.org/c3ref/db_config.html).

## 8. Extending SQLite

SQLite includes interfaces that can be used to extend its functionality. Such routines include:

- [sqlite3_create_collation()](https://www.sqlite.org/c3ref/create_collation.html)
- [sqlite3_create_function()](https://www.sqlite.org/c3ref/create_function.html)
- [sqlite3_create_module()](https://www.sqlite.org/c3ref/create_module.html)
- [sqlite3_vfs_register()](https://www.sqlite.org/c3ref/vfs_find.html)

The [sqlite3_create_collation()](https://www.sqlite.org/c3ref/create_collation.html) interface is used to create new [collating sequences](https://www.sqlite.org/datatype3.html#collation) for sorting text. The [sqlite3_create_module()](https://www.sqlite.org/c3ref/create_module.html) interface is used to register new [virtual table](https://www.sqlite.org/vtab.html) implementations. The [sqlite3_vfs_register()](https://www.sqlite.org/c3ref/vfs_find.html) interface creates new [VFSes](https://www.sqlite.org/vfs.html).

The [sqlite3_create_function()](https://www.sqlite.org/c3ref/create_function.html) interface creates new SQL functions - either scalar or aggregate. The new function implementation typically makes use of the following additional interfaces:

- [sqlite3_aggregate_context()](https://www.sqlite.org/c3ref/aggregate_context.html)
- [sqlite3_result()](https://www.sqlite.org/c3ref/result_blob.html)
- [sqlite3_user_data()](https://www.sqlite.org/c3ref/user_data.html)
- [sqlite3_value()](https://www.sqlite.org/c3ref/value_blob.html)

All of the built-in SQL functions of SQLite are created using exactly these same interfaces. Refer to the SQLite source code, and in particular the [date.c](https://sqlite.org/src/doc/trunk/src/date.c) and [func.c](https://sqlite.org/src/doc/trunk/src/func.c) source files for examples.

Shared libraries or DLLs can be used as [loadable extensions](https://www.sqlite.org/loadext.html) to SQLite.
