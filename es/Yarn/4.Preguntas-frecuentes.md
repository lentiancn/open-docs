# Preguntas Frecuentes de Yarn

## Preguntas Relacionadas con Versiones

### ¿Por qué el paquete yarn en npm sigue siendo 1.x?
Las versiones Modernas de Yarn no se han distribuido en npm desde 2019. La razón es que muchas personas dependían de `npm install -g yarn` como parte de la construcción de sus imágenes, y cualquier cambio rotundo rompería sus despliegues.

Como resultado, el equipo de Yarn decidió retirar el paquete yarn de npm y usarlo solo para versiones de mantenimiento 1.x. Yarn Moderno ahora se instala directamente desde el sitio web mediante Corepack o `yarn set version`.

### ¿Por qué debería actualizar a Yarn Moderno?
Aunque Yarn Classic (1.x) sigue siendo importante en el ecosistema JavaScript, se recomienda actualizar cuando sea posible:

- **Nuevas Funciones**: Más allá de las funciones clásicas, Moderno ofrece plugins que extienden funcionalidades como changesets, constraints, workspaces, etc.
- **Eficiencia**: Nuevas estrategias de instalación reducen significativamente el tamaño del proyecto (por ejemplo, los artefactos CRA se redujeron de 237MB a 45MB)
- **Extensibilidad**: Construye tus propias funciones según tus especificaciones sin esperar a la implementación oficial
- **Estabilidad**: Corrige problemas de diseño de larga data de Classic
- **Preparado para el Futuro**: La arquitectura Moderna permite un desarrollo de funciones más rápido

### ¿Qué tan difícil es la migración de Classic a Moderno?
Generalmente, hay que abordar algunos problemas principales:

1. **Cambio de Formato de Configuración**: Ya no lee `.npmrc` o `.yarnrc`, usa `.yarnrc.yml` en su lugar
2. **Dependencias de Paquetes de Terceros**: Algunos paquetes no listan correctamente las dependencias, requiriendo correcciones con `packageExtensions`
3. **Soporte de Editor**: Requiere configuración única de SDK
4. **Compatibilidad de Herramientas**: Herramientas como React Native y Flow pueden necesitar la estrategia de enlazador `node_modules`

La mayoría de los proyectos pueden completar la migración en medio día de trabajo.

## Preguntas de Uso

### ¿Qué archivos deben ignorarse en .gitignore?
**Al usar Zero-Installs**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Al no usar Zero-Installs**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Explicación de Archivos**:
- `.yarn/cache` y `.pnp.*`: Se pueden ignorar de forma segura, pero requieren `yarn install` después de cambiar de rama
- `.yarn/patches`: Contiene archivos de parche, debe comprometerse en el repositorio
- `.yarn/plugins` y `.yarn/releases`: Contiene versiones de Yarn, se recomienda comprometer para consistencia del equipo
- `yarn.lock`: Siempre debe comprometerse en el repositorio

### ¿Yarn soporta ESM?
Sí, Yarn soporta ESM.

Yarn soporta la estrategia de instalación `node-modules`, idéntica a la instalación de npm. Para el modo PnP (Plug'n'Play), el soporte ESM ha estado disponible desde la versión 3.1 a través de Node Loaders.

### ¿Deben comprometerse los archivos de bloqueo en el repositorio?
**Sí, siempre compromételos**.

Independientemente de si estás desarrollando aplicaciones independientes o bibliotecas distribuidas, los archivos de bloqueo deben almacenarse con el código fuente del proyecto. Esto asegura:
- Experiencia de desarrollo consistente para todos los contribuyentes
- Que el proyecto siga siendo construible en el futuro
- Evita problemas de deriva de versiones de dependencias

Las pruebas de integración continua deben manejarse por sistemas CI, no omitiendo archivos de bloqueo.

## Preguntas de Arquitectura Técnica

### ¿Yarn es operado por Facebook?
No. Aunque Yarn fue inicialmente implementado por un empleado de Facebook, el equipo actual de desarrollo activo consiste enteramente en empleados de empresas no fundadoras. Las contribuciones de empleados de Facebook pasan por el mismo proceso de revisión que otros contribuyentes.

### ¿Qué es registry.yarnpkg.com? ¿Facebook nos rastrea?
`registry.yarnpkg.com` es solo un registro CNAME que apunta al registro npm, sin servidor backend. El equipo de Yarn mantiene este nombre de host por fiabilidad—si la fuente principal se vuelve indisponible, puede redirigir a una copia de solo lectura del registro.

Yarn recopila telemetría básica del lado del cliente, pero ningún registro HTTP llega a la infraestructura del proyecto Yarn, mucho menos a Facebook.

### ¿Yarn es más rápido que otros gestores de paquetes?
El rendimiento es relativo y temporal. Las principales diferencias de Yarn radican en prioridades y valores fundamentales:
- Prioriza la funcionalidad de workspaces porque los monorepos proporcionan valor significativo
- Invierte fuertemente en Plug'n'Play porque es importante para el ecosistema
- Toma decisiones autónomas basadas en la hoja de ruta del proyecto

### ¿Por qué se parchea TypeScript incluso si no uso Plug'n'Play?
Yarn aplica automáticamente parches de soporte PnP de TypeScript a las versiones de TypeScript descargadas porque:

1. **Consistencia**: Asegura un comportamiento consistente entre entornos de desarrollo (node_modules) y producción (PnP)
2. **Consistencia de Caché**: Previene diferencias en caché de paquetes que podrían romper instalaciones inmutables
3. **Inofensivo**: El parche es una operación nula si PnP no está habilitado
4. **Contribución Comunitaria**: Espera eventualmente fusionar este PR en la rama principal de TypeScript

## Mejores Prácticas

### Compartir Scripts
Los nombres de scripts que contienen dos puntos (por ejemplo, `build:foo`) se pueden llamar desde cualquier workspace. Combinado con la variable de entorno `$INIT_CWD`, esto permite scripts reutilizables:

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

Luego llama desde cualquier workspace que contenga `tsconfig.json`:
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```
