# Questions fréquentes sur Yarn

## Questions liées aux versions

### Pourquoi le package yarn sur npm est-il toujours en version 1.x ?
Les versions modernes de Yarn ne sont pas distribuées sur npm depuis 2019. La raison est que de nombreuses personnes dépendaient de `npm install -g yarn` dans le cadre de la construction de leurs images, et tout changement cassant aurait rompu leurs déploiements.

En conséquence, l'équipe Yarn a décidé de retirer le package yarn de npm et de l'utiliser uniquement pour les versions de maintenance 1.x. Yarn moderne est désormais installé directement depuis le site web via Corepack ou `yarn set version`.

### Pourquoi devriez-vous passer à Yarn moderne ?
Bien que Yarn Classic (1.x) reste important dans l'écosystème JavaScript, une mise à niveau est recommandée lorsque cela est possible :

- **Nouvelles fonctionnalités** : Au-delà des fonctionnalités classiques, Modern offre des plugins étendant les fonctionnalités comme changesets, constraints, workspaces, etc.
- **Efficacité** : Les nouvelles stratégies d'installation réduisent considérablement la taille du projet (par exemple, les artefacts CRA ont été réduits de 237 Mo à 45 Mo)
- **Extensibilité** : Construisez vos propres fonctionnalités selon vos spécifications sans attendre l'implémentation officielle
- **Stabilité** : Corrige les problèmes de conception de longue date de Classic
- **Prêt pour l'avenir** : L'architecture moderne permet un développement de fonctionnalités plus rapide

### Quelle est la difficulté de la migration de Classic à Modern ?
Généralement, quelques problèmes principaux doivent être abordés :

1. **Changement de format de configuration** : Ne lit plus `.npmrc` ou `.yarnrc`, utilise `.yarnrc.yml` à la place
2. **Dépendances de packages tiers** : Certains packages ne listent pas correctement leurs dépendances, nécessitant des corrections avec `packageExtensions`
3. **Support de l'éditeur** : Nécessite une configuration SDK unique
4. **Compatibilité des outils** : Des outils comme React Native et Flow peuvent nécessiter la stratégie de lien `node_modules`

La majorité des projets peuvent compléter la migration en une demi-journée de travail.

## Questions d'utilisation

### Quels fichiers doivent être ajoutés à .gitignore ?
**Lors de l'utilisation de Zero-Installs** :
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Lorsqu'on n'utilise pas Zero-Installs** :
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Explication des fichiers** :
- `.yarn/cache` et `.pnp.*` : Peuvent être ignorés en toute sécurité, mais nécessitent `yarn install` après un changement de branche
- `.yarn/patches` : Contient des fichiers de correctifs, doit être commité dans le dépôt
- `.yarn/plugins` et `.yarn/releases` : Contient les versions de Yarn, il est recommandé de les commiter pour la cohérence de l'équipe
- `yarn.lock` : Doit toujours être commité dans le dépôt

### Yarn prend-il en charge ESM ?
Oui, Yarn prend en charge ESM.

Yarn prend en charge la stratégie d'installation `node-modules`, identique à l'installation npm. Pour le mode PnP (Plug'n'Play), le support ESM est disponible depuis la version 3.1 via Node Loaders.

### Les fichiers de verrouillage doivent-ils être commités dans le dépôt ?
**Oui, toujours les commiter**.

Qu'il s'agisse d'applications autonomes ou de bibliothèques distribuées, les fichiers de verrouillage doivent être stockés avec le code source du projet. Cela garantit :
- Une expérience développeur cohérente pour tous les contributeurs
- Que le projet reste constructible à l'avenir
- Évite les problèmes de dérive de versions de dépendances

Les tests d'intégration continue doivent être gérés par les systèmes CI, et non en omettant les fichiers de verrouillage.

## Questions d'architecture technique

### Yarn est-il exploité par Facebook ?
Non. Bien que Yarn ait été initialement implémenté par un employé de Facebook, l'équipe actuelle de développement actif est composée exclusivement d'employés d'entreprises non fondatrices. Les contributions des employés de Facebook suivent le même processus de révision que les autres contributeurs.

### Qu'est-ce que registry.yarnpkg.com ? Facebook nous suit-il ?
`registry.yarnpkg.com` est simplement un enregistrement CNAME pointant vers le registre npm, sans serveur backend. L'équipe Yarn conserve ce nom d'hôte pour des raisons de fiabilité – si la source principale devient indisponible, elle peut rediriger vers une copie en lecture seule du registre.

Yarn collecte des données de télémétrie basiques côté client, mais aucun journal HTTP n'atteint l'infrastructure du projet Yarn, encore moins Facebook.

### Yarn est-il plus rapide que les autres gestionnaires de paquets ?
Les performances sont relatives et temporaires. Les principales différences de Yarn résident dans les priorités et les valeurs fondamentales :
- Priorise la fonctionnalité des workspaces car les monorepos apportent une valeur significative
- Investit fortement dans Plug'n'Play car c'est important pour l'écosystème
- Prend des décisions autonomes basées sur la feuille de route du projet

### Pourquoi TypeScript est-il patché même si je n'utilise pas Plug'n'Play ?
Yarn applique automatiquement des correctifs de support PnP TypeScript aux versions TypeScript téléchargées parce que :

1. **Cohérence** : Assure un comportement cohérent entre les environnements de développement (node_modules) et de production (PnP)
2. **Cohérence du cache** : Empêche les différences de cache de packages qui pourraient casser les installations immuables
3. **Inoffensif** : Le correctif est une opération nulle si PnP n'est pas activé
4. **Contribution communautaire** : Espère finalement fusionner cette PR dans la branche principale de TypeScript

## Bonnes pratiques

### Partage de scripts
Les noms de scripts contenant des deux-points (par exemple, `build:foo`) peuvent être appelés depuis n'importe quel workspace. Combiné avec la variable d'environnement `$INIT_CWD`, cela permet des scripts réutilisables :

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

Ensuite, appelez depuis n'importe quel workspace contenant `tsconfig.json` :
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```
