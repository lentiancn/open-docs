# Yarn 常见问题

## 版本相关问题

### 为什么 npm 上的 yarn 包仍然是 1.x 版本？
Yarn Modern 版本自 2019 年起就不再通过 npm 分发。原因是许多用户依赖 `npm install -g yarn` 作为镜像构建的一部分，任何破坏性更改都会影响所有使用此模式的用户并破坏部署。

因此，Yarn 团队决定停用 npm 上的 yarn 包，仅用于少数 1.x 维护版本。现代 Yarn 现在直接从官方网站安装，通过 Corepack 或 `yarn set version` 命令。

### 为什么要升级到 Yarn Modern？
虽然 Yarn Classic (1.x) 仍然是 JavaScript 生态系统的重要组成部分，但建议尽可能升级：

- **新功能**: 除了经典功能外，Modern 还提供插件扩展功能，如 changesets、constraints、workspaces 等
- **效率**: 新的安装策略使项目体积大幅减小（例如 CRA 工件从 237MB 减少到 45MB）
- **可扩展性**: 可以根据需要构建自己的功能，无需等待官方实现
- **稳定性**: 修复了 Classic 中长期存在的设计问题
- **面向未来**: Modern 架构允许更快地构建新功能

### 从 Classic 迁移到 Modern 的难度如何？
通常需要处理以下几个主要问题：

1. **配置格式变更**: 不再读取 `.npmrc` 或 `.yarnrc` 文件，而是使用 `.yarnrc.yml` 文件
2. **第三方包依赖**: 某些包未正确列出依赖，需要通过 `packageExtensions` 设置进行修复
3. **编辑器支持**: 需要运行一次性的 SDK 设置
4. **特定工具兼容性**: React Native 和 Flow 等工具可能需要降级到 `node_modules` 安装策略

大多数项目只需半天工作即可完成迁移。

## 使用问题

### 哪些文件应该加入 .gitignore？
**使用 Zero-Installs 时**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**不使用 Zero-Installs 时**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**文件说明**:
- `.yarn/cache` 和 `.pnp.*`: 可安全忽略，但切换分支时需要重新运行 `yarn install`
- `.yarn/patches`: 包含 patch 文件，必须提交到仓库
- `.yarn/plugins` 和 `.yarn/releases`: 包含 Yarn 发布版本，建议提交以确保团队一致性
- `yarn.lock`: 始终应该提交到仓库

### Yarn 是否支持 ESM？
是的，Yarn 支持 ESM。

Yarn 支持 `node-modules` 安装策略，与 npm 安装方式完全相同。对于 PnP (Plug'n'Play) 模式，自 3.1 版本起也支持 ESM，通过 Node Loaders 实现。

### lockfiles 是否应该提交到仓库？
**是的，始终应该提交**。

无论开发独立应用还是分发库，lockfiles 都应该与项目源码一起存储。这确保了：
- 所有贡献者获得一致的开发体验
- 项目在未来仍可正常构建
- 避免依赖版本漂移问题

持续集成测试应该由 CI 系统处理，而不是通过不提交 lockfile 来实现。

## 技术架构问题

### Yarn 是否由 Facebook 运营？
不是。虽然 Yarn 最初由 Facebook 员工实现，但现在活跃的开发团队完全由非创始公司员工组成。Facebook 员工的贡献需要经过与其他贡献者相同的审查流程。

### registry.yarnpkg.com 是什么？Facebook 是否在跟踪用户？
`registry.yarnpkg.com` 只是指向 npm 注册表的 CNAME 记录，没有后端服务器。Yarn 团队保留此主机名是为了可靠性考虑，如果主源不可用，可以重定向到注册表的只读副本。

Yarn 收集一些基本的客户端遥测数据，但没有任何 HTTP 日志会到达 Yarn 项目基础设施，更不用说 Facebook。

### Yarn 是否比其他包管理器更快？
性能是相对且临时的状态。Yarn 的主要差异在于优先级和核心价值观：
- 优先考虑工作区功能，因为单体仓库提供了重要价值
- 投入大量资源推动 Plug'n'Play，因为这对生态系统很重要
- 根据项目路线图做出自主决策

### 为什么即使不使用 Plug'n'Play，TypeScript 也会被修补？
Yarn 会自动将 TypeScript 的 PnP 支持补丁应用到下载的 TypeScript 版本中，原因包括：

1. **一致性**: 确保开发环境（node_modules）和生产环境（PnP）的行为一致
2. **缓存一致性**: 避免因补丁差异导致包缓存不同，破坏不可变安装
3. **无害性**: 如果未启用 PnP，补丁实际上是空操作
4. **社区贡献**: 希望最终将此 PR 合并到 TypeScript 主分支

## 最佳实践

### 脚本共享
包含冒号的脚本名称（如 `build:foo`）可以从任何工作区调用。结合 `$INIT_CWD` 环境变量，可以编写可重用的脚本：

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

然后在任何包含 `tsconfig.json` 的工作区中调用：
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```

> **注意**: 本文档基于官方 yarnpkg.com 网站的 QA 页面内容整理，涵盖各版本的常见问题和最佳实践。
