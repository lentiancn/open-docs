# Yarn Häufig gestellte Fragen

## Versionsbezogene Fragen

### Warum ist das Yarn-Paket auf npm immer noch auf 1.x?
Yarn Modern-Versionen werden seit 2019 nicht mehr über npm verteilt. Der Grund dafür ist, dass viele Menschen auf `npm install -g yarn` als Teil ihres Image-Builds angewiesen waren, und jede Breaking-Änderung ihre Deployments unterbrechen würde.

Als Ergebnis entschied sich das Yarn-Team, das Yarn-npm-Paket einzustellen und es nur für 1.x-Wartungsreleases zu verwenden. Modernes Yarn wird jetzt direkt von der Website über Corepack oder `yarn set version` installiert.

### Warum sollte man auf Yarn Modern aktualisieren?
Obwohl Yarn Classic (1.x) im JavaScript-Ökosystem weiterhin eine wichtige Rolle spielt, wird ein Upgrade empfohlen, wenn möglich:

- **Neue Funktionen**: Neben klassischen Funktionen bietet Modern Plugins zur Erweiterung der Funktionalität wie Changesets, Constraints, Workspaces usw.
- **Effizienz**: Neue Installationsstrategien reduzieren die Projektgröße erheblich (z.B. wurden CRA-Artefakte von 237MB auf 45MB reduziert)
- **Erweiterbarkeit**: Bauen Sie Ihre eigenen Funktionen gemäß Ihren Spezifikationen, ohne auf die offizielle Implementierung warten zu müssen
- **Stabilität**: Behebt langjährige Designprobleme aus Classic
- **Zukunftssicherheit**: Die moderne Architektur ermöglicht eine schnellere Feature-Entwicklung

### Wie schwierig ist die Migration von Classic zu Modern?
Im Allgemeinen müssen einige Hauptprobleme angegangen werden:

1. **Änderung des Konfigurationsformats**: Liest nicht mehr `.npmrc` oder `.yarnrc`, sondern verwendet stattdessen `.yarnrc.yml`
2. **Abhängigkeiten von Drittanbieter-Paketen**: Einige Pakete listen Abhängigkeiten nicht korrekt auf und erfordern Korrekturen mit `packageExtensions`
3. **Editor-Unterstützung**: Erfordert einmalige SDK-Einrichtung
4. **Tool-Kompatibilität**: Tools wie React Native und Flow benötigen möglicherweise die `node_modules`-Linker-Strategie

Die meisten Projekte können die Migration in einem halben Arbeitstag abschließen.

## Verwendungsfragen

### Welche Dateien sollten in .gitignore aufgenommen werden?
**Bei Verwendung von Zero-Installs**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Ohne Zero-Installs**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Dateierklärungen**:
- `.yarn/cache` und `.pnp.*`: Können sicher ignoriert werden, erfordern aber nach dem Branch-Wechsel `yarn install`
- `.yarn/patches`: Enthält Patch-Dateien, muss im Repository committet werden
- `.yarn/plugins` und `.yarn/releases`: Enthält Yarn-Releases, sollte zur Team-Konsistenz committet werden
- `yarn.lock`: Sollte immer im Repository committet werden

### Unterstützt Yarn ESM?
Ja, Yarn unterstützt ESM.

Yarn unterstützt die `node-modules`-Installationsstrategie, identisch mit der npm-Installation. Für den PnP (Plug'n'Play)-Modus steht ESM-Support seit Version 3.1 über Node Loaders zur Verfügung.

### Sollten Lockfiles im Repository committet werden?
**Ja, immer committen**.

Unabhängig davon, ob Sie eigenständige Anwendungen oder verteilte Bibliotheken entwickeln, sollten Lockfiles zusammen mit dem Projektquellcode gespeichert werden. Dies stellt sicher:
- Konsistente Entwicklererfahrung für alle Mitwirkenden
- Das Projekt bleibt auch in Zukunft baubar
- Vermeidung von Abhängigkeitsversions-Drift-Problemen

Continuous Integration-Tests sollten von CI-Systemen behandelt werden, nicht durch das Weglassen von Lockfiles.

## Technische Architekturfragen

### Wird Yarn von Facebook betrieben?
Nein. Obwohl Yarn ursprünglich von einem Facebook-Mitarbeiter implementiert wurde, besteht das aktuelle aktive Entwicklungsteam ausschließlich aus Mitarbeitern nicht-gründender Unternehmen. Beiträge von Facebook-Mitarbeitern durchlaufen denselben Überprüfungsprozess wie andere Mitwirkende.

### Was ist registry.yarnpkg.com? Verfolgt Facebook uns?
`registry.yarnpkg.com` ist nur ein CNAME-Eintrag, der auf die npm-Registry verweist, ohne Backend-Server. Das Yarn-Team behält diesen Hostnamen aus Gründen der Zuverlässigkeit bei – falls die primäre Quelle nicht verfügbar wird, kann auf eine schreibgeschützte Registry-Kopie umgeleitet werden.

Yarn sammelt grundlegende clientseitige Telemetriedaten, aber keine HTTP-Logs erreichen die Yarn-Projektinfrastruktur, geschweige denn Facebook.

### Ist Yarn schneller als andere Paketmanager?
Leistung ist relativ und temporär. Die Hauptunterschiede von Yarn liegen in Prioritäten und Kernwerten:
- Priorisiert Workspace-Funktionalität, da Monorepos erheblichen Wert bieten
- Investiert stark in Plug'n'Play, da dies für das Ökosystem wichtig ist
- Trifft autonome Entscheidungen basierend auf der Projekt-Roadmap

### Warum wird TypeScript gepatcht, selbst wenn ich Plug'n'Play nicht verwende?
Yarn wendet automatisch TypeScript PnP-Support-Patches auf heruntergeladene TypeScript-Versionen an, weil:

1. **Konsistenz**: Stellt konsistentes Verhalten zwischen Entwicklungs- (node_modules) und Produktionsumgebung (PnP) sicher
2. **Cache-Konsistenz**: Verhindert Paket-Cache-Unterschiede, die immutable Installs brechen könnten
3. **Unbedenklich**: Der Patch ist ein No-Op, wenn PnP nicht aktiviert ist
4. **Community-Beitrag**: Hofft, diesen PR irgendwann in den TypeScript-Main-Branch zu mergen

## Best Practices

### Skriptfreigabe
Skriptnamen, die Doppelpunkte enthalten (z.B. `build:foo`), können aus jedem Workspace aufgerufen werden. In Kombination mit der `$INIT_CWD`-Umgebungsvariable ermöglicht dies wiederverwendbare Skripte:

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

Dann rufen Sie aus jedem Workspace, der `tsconfig.json` enthält, auf:
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```
