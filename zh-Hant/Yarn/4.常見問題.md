# Yarn 常見問題

## 版本相關問題

### 為什麼 npm 上的 yarn 套件仍然是 1.x 版本？
Yarn Modern 版本自 2019 年起就不再透過 npm 發佈。原因是許多使用者依賴 `npm install -g yarn` 作為映像建置的一部分，任何破壞性更改都會影響所有使用此模式的使用者並破壞部署。

因此，Yarn 團隊決定停用 npm 上的 yarn 套件，僅用於少數 1.x 維護版本。現代 Yarn 現在直接從官方網站安裝，透過 Corepack 或 `yarn set version` 指令。

### 為什麼要升級到 Yarn Modern？
雖然 Yarn Classic (1.x) 仍然是 JavaScript 生態系統的重要組成部分，但建議盡可能升級：

- **新功能**: 除了經典功能外，Modern 還提供外掛擴充功能，如 changesets、constraints、workspaces 等
- **效率**: 新的安裝策略使專案體積大幅減小（例如 CRA 工件從 237MB 減少到 45MB）
- **可擴充性**: 可以根據需要建置自己的功能，無需等待官方實作
- **穩定性**: 修復了 Classic 中長期存在的設計問題
- **面向未來**: Modern 架構允許更快地建置新功能

### 從 Classic 遷移到 Modern 的難度如何？
通常需要處理以下幾個主要問題：

1. **配置格式變更**: 不再讀取 `.npmrc` 或 `.yarnrc` 檔案，而是使用 `.yarnrc.yml` 檔案
2. **第三方套件相依性**: 某些套件未正確列出相依性，需要透過 `packageExtensions` 設定進行修復
3. **編輯器支援**: 需要執行一次性的 SDK 設定
4. **特定工具相容性**: React Native 和 Flow 等工具可能需要降級到 `node_modules` 安裝策略

大多數專案只需半天工作即可完成遷移。

## 使用問題

### 哪些檔案應該加入 .gitignore？
**使用 Zero-Installs 時**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**不使用 Zero-Installs 時**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**檔案說明**:
- `.yarn/cache` 和 `.pnp.*`: 可安全忽略，但切換分支時需要重新執行 `yarn install`
- `.yarn/patches`: 包含 patch 檔案，必須提交到倉儲
- `.yarn/plugins` 和 `.yarn/releases`: 包含 Yarn 發布版本，建議提交以確保團隊一致性
- `yarn.lock`: 始終應該提交到倉儲

### Yarn 是否支援 ESM？
是的，Yarn 支援 ESM。

Yarn 支援 `node-modules` 安裝策略，與 npm 安裝方式完全相同。對於 PnP (Plug'n'Play) 模式，自 3.1 版本起也支援 ESM，透過 Node Loaders 實現。

### lockfiles 是否應該提交到倉儲？
**是的，始終應該提交**。

無論開發獨立應用還是分發庫，lockfiles 都應該與專案原始碼一起儲存。這確保了：
- 所有貢獻者獲得一致的開發體驗
- 專案在未來仍可正常建置
- 避免相依性版本漂移問題

持續整合測試應該由 CI 系統處理，而不是透過不提交 lockfile 來實現。

## 技術架構問題

### Yarn 是否由 Facebook 營運？
不是。雖然 Yarn 最初由 Facebook 員工實作，但現在活躍的開發團隊完全由非創始公司員工組成。Facebook 員工的貢獻需要經過與其他貢獻者相同的審查流程。

### registry.yarnpkg.com 是什麼？Facebook 是否在追蹤使用者？
`registry.yarnpkg.com` 只是指向 npm 註冊表的 CNAME 記錄，沒有後端伺服器。Yarn 困隊保留此主機名是為了可靠性考慮，如果主源不可用，可以重新導向到註冊表的唯讀副本。

Yarn 收集一些基本的用戶端遙測資料，但沒有任何 HTTP 日誌會到達 Yarn 專案基礎設施，更不用說 Facebook。

### Yarn 是否比其他套件管理器更快？
效能是相對且臨時的狀態。Yarn 的主要差異在於優先順序和核心價值觀：
- 優先考慮工作區功能，因為單體倉儲提供了重要價值
- 投入大量資源推動 Plug'n'Play，因為這對生態系統很重要
- 根據專案路線圖做出自主決策

### 為什麼即使不使用 Plug'n'Play，TypeScript 也會被修補？
Yarn 會自動將 TypeScript 的 PnP 支援修補套用到下載的 TypeScript 版本中，原因包括：

1. **一致性**: 確保開發環境（node_modules）和生產環境（PnP）的行為一致
2. **快取一致性**: 避免因修補差異導致套件快取不同，破壞不可變安裝
3. **無害性**: 如果未啟用 PnP，修補實際上是空操作
4. **社群貢獻**: 希望最終將此 PR 合併到 TypeScript 主分支

## 最佳實務

### 指令共享
包含冒號的指令名稱（如 `build:foo`）可以從任何工作區呼叫。結合 `$INIT_CWD` 環境變數，可以編寫可重用的指令：

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

然後在任何包含 `tsconfig.json` 的工作區中呼叫：
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```

> **注意**: 本文檔基於官方 yarnpkg.com 網站的 QA 頁面內容整理，涵蓋各版本的常見問題和最佳實務。
