# Yarn 자주 묻는 질문

## 버전 관련 질문

### 왜 npm의 yarn 패키지가 여전히 1.x 버전인가요?
Yarn Modern 릴리스는 2019년 이후 npm을 통해 배포되지 않았습니다. 그 이유는 많은 사람들이 이미지 빌드의 일부로 `npm install -g yarn`에 의존하고 있었기 때문에, 어떤 중단 변경이라도 배포를 중단시킬 수 있었습니다.

결과적으로 Yarn 팀은 yarn npm 패키지를 폐기하고 1.x 유지보수 릴리스에만 사용하기로 결정했습니다. Modern Yarn은 이제 Corepack 또는 `yarn set version`을 통해 웹사이트에서 직접 설치됩니다.

### 왜 Yarn Modern으로 업그레이드해야 하나요?
Yarn Classic (1.x)이 JavaScript 생태계에서 중요한 역할을 계속하고 있지만, 가능하다면 업그레이드하는 것이 권장됩니다:

- **새로운 기능**: 클래식 기능 외에도 Modern은 changesets, constraints, workspaces 등의 기능을 확장하는 플러그인을 제공합니다.
- **효율성**: 새로운 설치 전략으로 프로젝트 크기가 크게 줄어듭니다 (예: CRA 아티팩트가 237MB에서 45MB로 감소)
- **확장성**: 공식 구현을 기다리지 않고 자신의 사양에 따라 자체 기능을 구축할 수 있습니다.
- **안정성**: Classic의 오래된 설계 문제를 해결합니다.
- **미래 대비**: Modern 아키텍처는 더 빠른 기능 개발을 가능하게 합니다.

### Classic에서 Modern으로 마이그레이션은 얼마나 어려운가요?
일반적으로 몇 가지 주요 문제를 해결해야 합니다:

1. **설정 형식 변경**: `.npmrc` 또는 `.yarnrc`를 더 이상 읽지 않고 대신 `.yarnrc.yml`을 사용합니다.
2. **서드파티 패키지 의존성**: 일부 패키지는 의존성을 제대로 나열하지 않아 `packageExtensions`를 통해 수정이 필요합니다.
3. **에디터 지원**: 일회성 SDK 설정이 필요합니다.
4. **도구 호환성**: React Native 및 Flow와 같은 도구는 `node_modules` 링커 전략으로 다운그레이드가 필요할 수 있습니다.

대부분의 프로젝트는 하루 정도의 작업으로 마이그레이션을 완료할 수 있습니다.

## 사용 관련 질문

### .gitignore에 어떤 파일을 추가해야 하나요?
**Zero-Installs 사용 시**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Zero-Installs 미사용 시**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**파일 설명**:
- `.yarn/cache` 및 `.pnp.*`: 안전하게 무시할 수 있지만, 브랜치 전환 후 `yarn install`이 필요합니다.
- `.yarn/patches`: 패치 파일을 포함하며, 저장소에 커밋되어야 합니다.
- `.yarn/plugins` 및 `.yarn/releases`: Yarn 릴리스를 포함하며, 팀 일관성을 위해 커밋하는 것이 좋습니다.
- `yarn.lock`: 항상 저장소에 커밋되어야 합니다.

### Yarn은 ESM을 지원하나요?
네, Yarn은 ESM을 지원합니다.

Yarn은 `node-modules` 설치 전략을 지원하며, 이는 npm 설치와 동일합니다. PnP (Plug'n'Play) 모드의 경우, 버전 3.1부터 Node Loaders를 통해 ESM 지원이 가능합니다.

### 잠금 파일을 저장소에 커밋해야 하나요?
**네, 항상 커밋해야 합니다**.

독립형 애플리케이션을 개발하든 배포 라이브러리를 개발하든 관계없이, 잠금 파일은 프로젝트 소스 코드와 함께 저장되어야 합니다. 이를 통해 다음을 보장합니다:
- 모든 기여자가 일관된 개발 경험을 얻을 수 있음
- 미래에도 프로젝트를 빌드할 수 있음
- 의존성 버전 드리프트 문제를 방지

지속적 통합 테스트는 CI 시스템에서 처리되어야 하며, 잠금 파일을 생략함으로써 이루어져서는 안 됩니다.

## 기술 아키텍처 관련 질문

### Yarn은 Facebook에서 운영하나요?
아니요. Yarn은 처음에 Facebook 직원이 구현했지만, 현재 활발한 개발 팀은 비창립 기업의 직원들로만 구성되어 있습니다. Facebook 직원의 기여도 다른 기여자들과 동일한 검토 프로세스를 거칩니다.

### registry.yarnpkg.com이란 무엇인가요? Facebook이 우리를 추적하나요?
`registry.yarnpkg.com`은 백엔드 서버 없이 npm 레지스트리를 가리키는 CNAME 레코드일 뿐입니다. Yarn 팀은 신뢰성을 위해 이 호스트 이름을 유지합니다. 기본 소스를 사용할 수 없게 되면 읽기 전용 레지스트리 복사본으로 리디렉션할 수 있습니다.

Yarn은 기본적인 클라이언트 측 원격 측정 데이터를 수집하지만, HTTP 로그는 Yarn 프로젝트 인프라에 도달할 수 없으며, Facebook에 더더욱 도달할 수 없습니다.

### Yarn이 다른 패키지 매니저보다 빠른가요?
성능은 상대적이며 일시적인 상태입니다. Yarn의 주요 차이점은 우선순위와 핵심 가치에 있습니다:
- 모노레포가 중요한 가치를 제공하기 때문에 워크스페이스 기능을 우선시함
- 생태계에 중요하기 때문에 Plug'n'Play에 많은 자원을 투자함
- 프로젝트 로드맵을 기반으로 자율적인 결정을 내림

### Plug'n'Play를 사용하지 않더라도 TypeScript가 패치되는 이유는 무엇인가요?
Yarn은 다운로드된 TypeScript 버전에 TypeScript PnP 지원 패치를 자동으로 적용합니다. 그 이유는:

1. **일관성**: 개발 환경(node_modules)과 프로덕션 환경(PnP) 간의 일관된 동작을 보장
2. **캐시 일관성**: 패키지 캐시 차이로 인해 불변 설치가 깨지는 것을 방지
3. **무해성**: PnP가 활성화되지 않은 경우 패치는 실제로 아무 작업도 수행하지 않음
4. **커뮤니티 기여**: 언젠가는 이 PR을 TypeScript 메인 브랜치에 병합할 수 있기를 희망

## 모범 사례

### 스크립트 공유
콜론을 포함하는 스크립트 이름(예: `build:foo`)은 모든 워크스페이스에서 호출할 수 있습니다. `$INIT_CWD` 환경 변수와 결합하면 재사용 가능한 스크립트를 작성할 수 있습니다:

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

그런 다음 `tsconfig.json`을 포함하는 모든 워크스페이스에서 호출합니다:
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```

> **참고**: 이 문서는 yarnpkg.com FAQ 페이지의 공식 콘텐츠를 기반으로 하며, 모든 버전에 대한 일반적인 질문과 모범 사례를 다룹니다.
