# Yarn よくある質問

## バージョン関連の質問

### なぜ npm 上の yarn パッケージはまだ 1.x バージョンなのですか？
Yarn Modern リリースは 2019 年以降、npm で配布されていません。その理由は、多くの人々がイメージビルドの一部として `npm install -g yarn` に依存しており、破壊的な変更がデプロイを破壊してしまうためです。

その結果、Yarn チームは yarn npm パッケージを廃止し、1.x のメンテナンスリリースのみに使用することにしました。Modern Yarn は現在、Web サイトから直接 Corepack または `yarn set version` を介してインストールされています。

### なぜ Yarn Modern にアップグレードすべきですか？
Yarn Classic (1.x) は JavaScript エコシステムにおいて重要な役割を果たしていますが、可能な場合はアップグレードすることを推奨します：

- **新機能**: クラシック機能に加えて、changesets、constraints、workspaces などのプラグインによる機能拡張
- **効率性**: 新しいインストール戦略によりプロジェクトサイズが大幅に削減（例：CRA アーティファクトが 237MB から 45MB に）
- **拡張性**: 公式実装を待つことなく、自分の仕様に従って独自の機能を構築可能
- **安定性**: Classic に存在していた長年の設計上の問題を修正
- **将来性**: Modern アーキテクチャにより新機能の開発がより迅速に可能

### Classic から Modern への移行はどのくらい難しいですか？
通常、以下のいくつかの主要な問題に対処する必要があります：

1. **設定フォーマットの変更**: `.npmrc` や `.yarnrc` を読み込まなくなり、代わりに `.yarnrc.yml` を使用
2. **サードパーティパッケージの依存関係**: 一部のパッケージが依存関係を正しくリストしていないため、`packageExtensions` での修正が必要
3. **エディタサポート**: 一度限りの SDK 設定が必要
4. **ツールの互換性**: React Native や Flow などのツールでは `node_modules` リンカー戦略へのダウングレードが必要な場合がある

ほとんどのプロジェクトは半日程度の作業で移行を完了できます。

## 使用に関する質問

### どのファイルを .gitignore に追加すべきですか？
**Zero-Installs を使用する場合**:
```
.yarn/*
!.yarn/cache
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**Zero-Installs を使用しない場合**:
```
.pnp.*
.yarn/*
!.yarn/patches
!.yarn/plugins
!.yarn/releases
!.yarn/sdks
!.yarn/versions
```

**ファイルの説明**:
- `.yarn/cache` と `.pnp.*`: 安全に無視可能ですが、ブランチ切り替え後に `yarn install` を実行する必要があります
- `.yarn/patches`: パッチファイルを含み、リポジトリにコミットする必要があります
- `.yarn/plugins` と `.yarn/releases`: Yarn リリースを含み、チームの一貫性のためにコミットすることを推奨
- `yarn.lock`: 常にリポジトリにコミットする必要があります

### Yarn は ESM をサポートしていますか？
はい、Yarn は ESM をサポートしています。

Yarn は `node-modules` インストール戦略をサポートしており、npm インストールと同一です。PnP (Plug'n'Play) モードでは、バージョン 3.1 以降で Node Loaders を通じて ESM サポートが利用可能です。

### lockfiles はリポジトリにコミットすべきですか？
**はい、常にコミットしてください**。

スタンドアロンアプリケーションか配布ライブラリかに関わらず、lockfiles はプロジェクトソースコードと一緒に保存する必要があります。これにより：
- すべてのコントリビューターが一貫した開発体験を得られる
- 将来的にもプロジェクトがビルド可能であることが保証される
- 依存関係のバージョンドリフト問題を回避できる

継続的インテグレーションテストは CI システムで処理すべきであり、lockfile を省略することで実現すべきではありません。

## 技術的アーキテクチャに関する質問

### Yarn は Facebook によって運営されていますか？
いいえ。Yarn は当初 Facebook 社員によって実装されましたが、現在のアクティブ開発チームは非創業企業の社員のみで構成されています。Facebook 社員の貢献も他の貢献者と同じレビュープロセスを経る必要があります。

### registry.yarnpkg.com とは何ですか？Facebook はユーザーを追跡していますか？
`registry.yarnpkg.com` は npm レジストリを指す CNAME レコードにすぎず、バックエンドサーバーはありません。Yarn チームがこのホスト名を維持しているのは信頼性のためです。プライマリソースが利用不可になった場合、読み取り専用のレジストリコピーにリダイレクトできます。

Yarn は基本的なクライアントサイドテレメトリを収集しますが、HTTP ログが Yarn プロジェクトインフラストラクチャに到達することはありません。ましてや Facebook には到達しません。

### Yarn は他のパッケージマネージャーより高速ですか？
パフォーマンスは相対的かつ一時的なものです。Yarn の主な違いは優先順位とコアバリューにあります：
- モノレポが重要な価値を提供するため、ワークスペース機能を優先
- エコシステムにとって重要であるため、Plug'n'Play に多大なリソースを投入
- プロジェクトロードマップに基づいて自律的な意思決定を行う

### Plug'n'Play を使用していない場合でも、なぜ TypeScript はパッチされるのですか？
Yarn はダウンロードされた TypeScript バージョンに TypeScript PnP サポートパッチを自動的に適用します。その理由は：

1. **一貫性**: 開発環境（node_modules）と本番環境（PnP）の動作を一貫させるため
2. **キャッシュの一貫性**: パッチの違いによりパッケージキャッシュが異なり、イミュータブルインストールが破壊されるのを防ぐため
3. **無害性**: PnP が有効になっていない場合、パッチは実際には何もしない（no-op）
4. **コミュニティ貢献**: 将来的にこの PR を TypeScript メインブランチにマージすることを目指しているため

## ベストプラクティス

### スクリプトの共有
コロンを含むスクリプト名（例：`build:foo`）は任意のワークスペースから呼び出すことができます。`$INIT_CWD` 環境変数と組み合わせることで、再利用可能なスクリプトを作成できます：

```json
{
  "scripts": {
    "g:tsc": "cd $INIT_CWD && tsc"
  }
}
```

その後、`tsconfig.json` を含む任意のワークスペースから呼び出します：
```json
{
  "scripts": {
    "build": "yarn g:tsc"
  }
}
```
